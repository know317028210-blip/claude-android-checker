# Claude 环境检测：逐项检测原理与判定规则

本文档说明 App 里每一项检测**查什么、依据是什么、什么情况算失败、怎么实现、失败时怎么降级**。

依据分三级，文中逐项标注：

| 标记 | 含义 |
|---|---|
| **【官方】** | Anthropic 服务条款、Supported Regions Policy、帮助中心明文规定 |
| **【逆向】** | 社区封号案例与公开逆向分析归纳出的隐性规则，非官方文档 |
| **【启发式】** | 本项目的工程判断，用于把公开数据变成可读结论，可能误判 |

> 重要前提：Claude 的风控不是"命中一条就封"，而是**积分制多维模型**——不同信号带不同权重，累计到阈值才触发 KYC 或封禁。所以本项目的评分是"风险画像"，不是"判决书"。

### 读不到数据时怎么判

这是最容易出错的地方：**没测到**和**测过没问题**是两件事，不能混为一谈。

统一规则：

| 情况 | 得分 | 显示 |
|---|---|---|
| 数据读到，结果正常 | 10/10 | 正常 |
| 数据读到，结果异常 | 按项扣分 | 异常 |
| **数据完全读不到** | **5/10** | **无法判定（数据未读到）** |
| 读到了但认不出（MCC 未收录、国家码非法） | 5/10 | 无法判定（地区未识别） |
| 设备没网 | 5/10 | 设备当前没有网络，无法判断 |

绝不出现"读不到就给满分"的情况。以下每项都做了区分：

| 检测项 | 曾有的误判 | 现在的处理 |
|---|---|---|
| 系统时区 | 时区名读不到 → 当成非中国时区给 10 | 读不到 → 无法判定 |
| 时区偏移 | 无时区名 → 无法比对却给 10 | 读不到 → 无法判定 |
| 系统语言 | 语言列表空 → 当成英文给 10 | 读不到 → 无法判定 |
| 中文语言变体 | 列表空 → 当成"没有中文"给 10 | 读不到 → 无法判定 |
| 系统区域设置 | 区域空 → 给 10 | 读不到 → 无法判定 |
| 中文字体栈 | 字体表读不到 → 当成"没有中文字体"给 10 | 读不到 → 无法判定 |
| 厂商预装字体 | 同上 → 给 10 | 读不到 → 无法判定 |
| SIM 与号码 | 桥接失效 → 报"没有插 SIM 卡"给 10 | 区分没插卡 / 明细受限 / 读不到 |
| 设备型号等 8 项 | 原生桥接失效 → 给 8（看着几乎没问题） | 统一 5/10 无法判定 |
| IPv6 泄露 | 查询失败 → 给 7 | 查询失败 → 无法判定；确认无出口才给 10 |
| 实时通信穿透 | 探不到 → 文案说"不确定"但给 9 | 有网但 WebRTC 无候选 = 无泄露通道（9）；无网 = 无法判定 |
| Claude 服务连通 | 三个域名全不通 → 直接判 2 | 先排除"设备根本没网"，断网报无法判定 |

**为什么统一用 5 分**：中间分表示"这项既没通过也没失败"。给 8 分等于暗示"基本没问题"，给 0 分等于误判为失败，两者都是不诚实。

**为什么 SIM 要分三种空状态**：

- `SIM` 为 null（桥接失效）→ 读不到 → 无法判定
- `simState=ABSENT`（确实没插卡）→ 没卡 → 10/10
- `simState=READY` 但拿不到卡明细（权限被拒）→ 有卡但读不到 → 8/10

把第一种报成"没有插 SIM 卡"，等于凭空断言了一件没验证的事。

---

### 为什么权重不是平均分配

若每项都是 10 分，会出现一个荒谬的结果：**设备型号判错，和 IP 落在不支持地区，扣分一样多**。但两者对账号的实际影响差着量级——前者顶多算画像里的一块拼图，后者是官方条款写死的硬门槛。

所以本项目的权重直接对齐"该项对 Claude 风控的真实分量"，并保证：

- **低权重项丢满也只丢 1 分**（设备型号、ROM 状态、代理隧道、服务连通），不会因为一个无关紧要的信号把总分拉垮；
- **高权重项丢满会重创总分**（IP 归属地 20 分、IP 类型 13 分），因为它们本身就是决定性的；
- **"待改进"只统计权重 ≥3 的项**，权重 1-2 的项不参与这个计数，避免"满屏待改进"的噪音。

单项得分 = 权重 × 得分率。例如设备型号得分率 80%，则得 0.8 / 1；IP 类型得分率 60%，则得 7.8 / 13。

## 二、指纹一致性（7 项）

### 1. 系统时区 【官方 + 逆向】

**查什么**：系统时区名（如 `Asia/Shanghai`）与出口 IP 的时区是否一致。

**隐藏规则**：
- 官方要求"用户必须物理位于支持地区"（Supported Regions Policy）。时区是唯一无法通过网络层伪造、又直接暴露物理位置的系统设置。
- 逆向观察：风控不只比较"时区名字"，还会把**时区与 IP 时区做交叉验证**。IP 在美国、时区是 UTC+8，是最典型的一对矛盾信号。
- 注意：时区单独一项通常不致命（大量海外华人用中文系统），但它是"最后一根稻草"型信号——基础分已经很高时，它会把总分推过阈值。

**失败判定**：
- `Asia/Shanghai`、`Asia/Urumqi`、`Asia/Chongqing`、`Asia/Harbin`、`Asia/Kashgar` → 1/10，并触发**一票否决**（官方地区政策直接冲突）
- `Asia/Hong_Kong`、`Asia/Macau`、`Asia/Taipei` → 5/10（港澳台时区，半权重）
- 其他 → 10/10
- 额外展示：与 IP 时区是否一致（不一致会明确写出来，供人工判断）

**怎么实现**：`Intl.DateTimeFormat().resolvedOptions().timeZone` + ip-api 返回的 `timezone` 字段做比对。

**降级**：IP 情报不可达时，仅按本地时区判定，不展示对照说明。

---

### 2. 时区偏移 【逆向】

**查什么**：`getTimezoneOffset()` 的数值。

**隐藏规则**：偏移是独立于时区名的第二个信号。改时区名但不重启、或系统锁定自动时区时，偏移可能仍是 +8——出现"名字对了、数值没对"的破绽。

**判定顺序**：
1. 先查一致性：时区名对应的标准偏移（内置 40+ 常见时区表）与实际偏移是否吻合。**不吻合 → 2/10**，这是"只改了一半"的明确证据。
2. 一致的情况下，若偏移仍是 `UTC+8` → 4/10（全球 UTC+8 不止中国，属中低权重）。
3. 其他 → 10/10。

**怎么实现**：`-new Date().getTimezoneOffset()/60` 取实际偏移，`Intl.DateTimeFormat().resolvedOptions().timeZone` 取时区名，查 `TZ_OFFSET` 表比对。

---

### 3. 系统语言 【逆向】

**查什么**：`navigator.languages` 的首位语言。

**隐藏规则**：语言列表是画像里权重最高的"软信号"之一——它不证明你在哪，但强烈暗示你属于哪个语言区。风控通常看**首位语言**，而不是"是否包含中文"。

**失败判定**：
- 首位为 `zh-CN` / `zh-Hans` / `zh` → 3/10
- 首位为其他 zh 变体 → 6/10
- 其他 → 10/10

**误判来源**：真正在美国生活的华人也会把中文设首位，所以这一项的权重被刻意压低（3/10 而非 0）。

---

### 4. 中文语言变体 【逆向】

**查什么**：语言列表里是否存在简体/繁体变体。

**隐藏规则**：比"首选语言"更细，用来区分大陆、港澳台、海外华人三类人群。即使英文在首位，列表里残留 `zh-CN` 仍会被记录。

**失败判定**：存在任一变体 → 5/10；无 → 10/10。

---

### 5. 系统区域设置 【逆向】

**查什么**：`Intl.DateTimeFormat().resolvedOptions().locale`（系统区域，不是界面语言）。

**隐藏规则**：界面语言和区域格式是**两套独立开关**。只把界面改成英文、区域仍是 zh-CN，会出现"表面英文、底层中文"的矛盾——这比纯中文环境更可疑，因为它在伪装。

**失败判定**：区域为 `zh-CN` / `zh-Hans` → 3/10；其他 zh → 6/10；非中文 → 10/10。

---

### 6. 中文字体栈 【逆向】

**查什么**：系统里实际安装的中文字体（读 `/system/etc/fonts.xml` 与 `/system/fonts` 文件名）。

**隐藏规则**：
- 字体是刷进系统分区的静态文件，改语言、改区域、改 UA 都动不了它，因此是"中文环境"最硬的物证之一。
- 网页端只能用 Canvas `measureText` 逐款试探（有误差），原生 App 可以直接读字体表，准确度更高。

**失败判定**：
- 检出厂商字体 + ≥2 款 CJK 字体 → 2/10
- 仅 ≥2 款 CJK 字体 → 6/10
- 仅 1 款 → 7/10
- 未检出 → 10/10

**误判来源**：几乎所有 Android 都预装 Noto CJK，所以"检出中文字体"本身不代表在中国——真正有区分度的是**厂商自有字体**（见下一项）。

---

### 7. 厂商预装字体 【逆向】

**查什么**：MiSans（小米）、HarmonyOS Sans（华为）、OPPO Sans、vivo Sans、Honor Sans、阿里巴巴普惠体等。

**隐藏规则**：这类字体只随国产行货 ROM 出厂，是设备来源的硬指纹；即便改 UA、换语言也去不掉。

**失败判定**：≥2 款 → 2/10；1 款 → 6/10；无 → 10/10。

**怎么实现**：原生层枚举 `/system/fonts` 文件名 + 解析 `fonts.xml` 的 `name=` 属性，两边合并匹配。

## 三、设备完整性（9 项）

### 8. SIM 与号码 【官方 + 系统数据】

**查什么**：SIM 卡的 MCC/MNC（运营商国家码）、物理卡还是 eSIM、几个卡槽、每张卡归属国、本机号码是否可读。

**隐藏规则**：
- 官方明文：注册验证**只接受支持地区、能收短信的实体号码**；VoIP、Google Voice、App 内生成号码、座机一律拒绝；一个号码最多验证 3 个账号，且验证后不可更换。
- 安卓版 Claude 客户端可读 SIM 归属国，但权重低（海外华人保留国内卡很常见）。
- MCC 由 SIM 卡出厂写入，是最硬的归属证据；eSIM 与实体卡在风控上略有差异（eSIM 更容易批量开通）。

**三态判定**：每张卡只有三种结论，没有"大概没问题"这第四种。

| 状态 | 触发条件 | 得分影响 |
|---|---|---|
| 支持 | MCC 解析出的国家不在限制名单 | 10/10（有可用卡） |
| 不支持 | 解析出 CN / HK / MO | 3/10（全部不支持） |
| **未知** | MCC 读不到、MCC 不在映射表、国家码不合法 | **6/10，标注"无法判定"** |

未知不等于通过。读不到就如实说读不到，给中间分，既不判死也不放行。

**失败判定**：
- 全部卡都在 CN/HK/MO → 3/10
- 有支持地区卡、也有不支持卡 → 6/10（并补一句"另有一张支持地区的卡"）
- 全部卡都认不出来 → 6/10（标注"无法判定（地区未识别）"）
- 无 SIM（纯 WiFi） → 10/10（无信号可读，不等于合格）

**MCC 覆盖率**：内置 229 个 MCC 映射，覆盖 220 个国家/地区。多国共用的 MCC（如 310 被美国、关岛、波多黎各共用）按该 MCC 下运营商数量取主归属，310 判为美国。表外的 MCC 一律走"未知"，不做猜测。

**怎么实现**：`SubscriptionManager.getActiveSubscriptionInfoList()` 取 mcc/mnc/countryIso/isEmbedded/service；`TelephonyManager.getLine1Number()` 判断号码可读性（需 `READ_PHONE_STATE`）。

**国家判定**：以 MCC 为准。`countryIso` 是系统层字段，无服务或 ROM 异常时可能是脏值（实测遇到过 MCC=460 却报 `us` 的机型），因此 MCC 缺失时才回退到 ISO。

**IP 侧同样三态**：国家码认不出时（非法 ISO、接口异常）给 5/10 并标"无法判定"，不按"非黑名单即通过"处理。

**显示原则**：测到什么显示什么，不套固定模板。单卡不标卡号；运营商名缺失就不显示；号码读到才显示后四位，读不到完全不提；无信号的卡标注"无服务"。内部判定细节（如 MCC 与 ISO 冲突）不呈现给用户。

**降级**：无权限时若 `simState=READY`，显示"读到了 SIM 卡，但卡信息被系统限制"，给 8/10，绝不谎报"无 SIM 卡"。

### 9. 设备型号 【逆向】

**查什么**：`Build.MANUFACTURER/MODEL/BRAND`。

**隐藏规则**：机型本身权重不高，但它是其他信号的"锚"——比如型号是国产机、字体是 MiSans、语言是中文，三者互相印证会显著加分。

**失败判定**：华为/鸿蒙 → 2/10；其他国产品牌 → 5/10；非国产 → 10/10。

---

### 10. Root / 框架 【逆向】

**查什么**：`su` 二进制路径、Magisk 目录（`/data/adb/magisk`、`/data/adb/modules`）、`Build.TAGS` 是否含 `test-keys`。

**隐藏规则**：Root 环境意味着设备指纹可被任意篡改，风控会把这类设备视为"不可信环境"；同一台 Root 设备上的多个账号极易被串联。

**失败判定**：命中任一 → 3/10；否则 10/10。

---

### 11. 模拟器检测 【逆向 · 一票否决】

**查什么**：`Build.FINGERPRINT`（generic/emulator/vbox）、`Build.HARDWARE`（goldfish/ranchu）、`Build.PRODUCT`、`Build.BRAND`、`ro.kernel.qemu`。

**隐藏规则**：云手机、模拟器、多开容器是批量注册的主要工具，一旦被识别基本等于进入黑名单。除了构建属性，真实设备还有传感器、GPU 型号、电池状态等可用于交叉验证。

**失败判定**：命中任一模拟器特征 → 1/10，并**一票否决**。

**误判风险**：极少数定制 ROM 会改坏 `Build.HARDWARE`，因此证据会一起展示，便于人工复核。

---

### 12. 系统 ROM 状态 【逆向】

**查什么**：`Build.TAGS`（是否 `release-keys`）、`Build.TYPE`（是否 `user`）、安全补丁级别。

**隐藏规则**：签名与构建类型能判断系统是否被改过。第三方 ROM 会让设备偏离普通用户画像，通常与其他异常叠加计分。

**失败判定**：非官方构建 → 5/10；官方 → 10/10。

---

### 13. 支付环境 【官方 + 启发式】

**查什么**：应用安装来源（`getInstallSourceInfo`）、是否有 Google 服务框架/Play、装了哪些支付类应用（支付宝/微信/云闪付/Google 钱包/PayPal）。

**隐藏规则**：
- 官方要求：账单地址必须与卡的发行国一致，卡段本身会被 Stripe 风控评估。
- 卡号在服务器侧，但本机会留下**体系痕迹**：从哪个商店安装应用、有没有 Google 服务、装了哪些支付工具，这三者组合基本能判出支付体系在国内还是海外。

**失败判定**：
- 来自 Google Play → 10/10
- 非商店安装但有 GMS → 6/10
- 无 GMS（国内应用体系）→ 4/10

**误判来源**：这是**推断**而非直接读取。侧载安装（如本项目）本身就会扣分，属于已知偏差。

---

### 14. 多开与分身 【逆向】

**查什么**：17 个常见多开/分身包名（平行空间、双开助手、VirtualApp、Island、Shelter、App Cloner 等）+ 系统用户配置数（`UserManager.getUserProfiles()`）。

**隐藏规则**：连坐看的是"同一设备上出现过哪些账号"。多开容器与工作资料，正是同设备多账号最直接的技术手段；设备指纹一旦关联，历史账号会被串成一条线。

**失败判定**：检出分身工具 → 2/10；存在多个用户配置 → 4/10；单一配置 → 10/10。

**误判来源**：部分厂商的"第二空间"与"应用双开"也会产生额外用户配置，因此该项只扣分、不否决。

---

### 15. 代理隧道状态 【启发式】

**查什么**：`ConnectivityManager` 是否存在 `TRANSPORT_VPN` 网络；系统 HTTP 代理属性。

**隐藏规则**：这一项本身不是风险——它只说明流量是否走了系统级隧道。真正的意义在于：**没开隧道时，下面的出口 IP 就是你本地网络的真实地址**。

**失败判定**：有 VPN → 10/10；无 → 6/10（仅提示，不否决）。

---

## 四、网络出口（6 项）

### 16. IP 归属地 【官方 · 一票否决】

**查什么**：出口 IP 的国家/地区。

**隐藏规则**：官方 Supported Regions Policy 明文规定，只有物理位于支持地区的人才能创建与使用账号。名单内**没有**中国大陆、香港、澳门、俄罗斯、白俄罗斯、伊朗、朝鲜、古巴、叙利亚；其余 185 个地区在列。协议还禁止不支持地区实体持股 >50% 的公司使用（与企业注册地无关）。

**失败判定**：命中不支持地区 → 0/10，并**一票否决**。

**怎么实现**：ip-api 的 `countryCode`（主源），ipwho.is 兜底。

---

### 17. IP 类型与纯净度 【逆向 · 多源交叉】

**查什么**：这是最容易骗人也最容易被骗的一项。同时向三个源取证：

| 证据 | 来源 | 说明 |
|---|---|---|
| 数据中心标记 `hosting` | ip-api | 机房 IP 的基础判定 |
| 代理标记 `proxy` / `mobile` | ip-api | 是否被公开标记为代理、是否移动网络 |
| 代理判定 `proxy` + `type` | proxycheck.io | `VPN` / `PUB` / `RES` / `Business` |
| ASN 归属 | 本地名单（40+ 批发机房） | Vultr、M247、DigitalOcean、Hetzner… |
| ASN 名称特征 | 本地正则 | 含 hosting / cloud / server / colo / vps |
| 反向解析 PTR | 两源 | 像服务器，或**是第三方域名** |

**隐藏规则（重点）**：
- 真正有区分度的不是"机房 vs 住宅"这个标签，而是**标签与事实是否自洽**。
- 市面上大量"家宽"是把机房 IP 换个名字卖。判定这类"假家宽"最有效的手段是 **PTR 归属**：真家宽的反向解析通常挂在运营商自有域名下（`*.ocn.ne.jp`、`c-73-24-110-12.hsd1.ma.comcast.net`）；而住宅代理节点往往解析到一个**第三方短域名**，与运营商毫无关系。
- 本项目实测样本：某日本"住宅"出口，ASN 属 Sony（消费级 ISP）、`hosting=false`、`proxy=no`，但 PTR 是 `hello.world` —— 与 Sony 无关，判定为住宅代理。

**失败判定（计票制）**：
- ≥2 条机房证据 → 1/10
- 1 条机房证据 → 3/10
- 0 条机房证据且 ≥2 条住宅证据 → 10/10
- 其余 → 6/10「无法确认」——**宁可说不确定，也不冒充住宅**

**降级**：两个源都不可达 → 6/10「多个情报接口都不可达」；仅 ip-api 可用 → 只用它的标记 + 本地 ASN/PTR 规则。

---

### 18. IPv6 泄露 【逆向 · 一票否决】

**查什么**：`api64.ipify.org` 返回的 IPv6 地址，与 IPv4 出口比对国家。

**双重取证**：`api64` 走原生请求时很可能优先用 IPv4 出去，返回的是 v4 地址。因此拿不到 v6 时会再用 WebRTC 候选地址补判一次，避免"IPv6 项说没有 v6、实时通信项却探到 v6 地址"这种自相矛盾。

**隐藏规则**：
- 绝大多数代理只接管 IPv4。访问支持 IPv6 的域名时，请求会从本地 v6 出口直接出去，绕过隧道——这是"明明挂了代理还是被封"最常见的原因。
- IPv6 的 **/32 前缀段直接标明运营商**（`240e` 中国电信、`2408` 联通、`2409` 移动），比地理位置还硬，查不到 geo 也能判定。
- "查不到 v6"分两种：查询成功但确实没有出口（10/10），和查询本身失败（7/10，标"无法确认"）。后者不能当作没问题。

**失败判定**：v6 与 v4 国家不一致 → 1/10，并**一票否决**；一致或无 v6 → 10/10。

---

### 19. 实时通信穿透 【逆向 · 一票否决】

**查什么**：用 STUN 建立探测通道，收集 ICE 候选地址（公网 / 内网 / mDNS）。

**隐藏规则**：
- WebRTC 为建立点对点连接会直接探测网卡地址，可绕过普通代理扩展，前端脚本能直接读到。
- 现代浏览器会把内网地址匿名化成 `.local`（mDNS），这本身也是指纹特征；若内网地址明文可见，说明是较老或异常的实现。
- 判定关键不是"是否泄露"，而是**泄露的地址与出口是否同一地区**——同地区泄露只是冗余，异地区泄露等于自证。

**失败判定**：泄露公网地址且与出口地区不一致 → 2/10，并**一票否决**；同地区或仅内网 → 8–10/10；探测受限 → 9/10「结果不确定」。

---

### 20. 时区与 IP 一致性 【逆向】

**查什么**：时区地区与 IP 地区是否指向同一处（复用第 1、16 项的数据做交叉）。

**隐藏规则**：风控从不只看单项。时区与 IP 是它最容易做、也最有效的一对交叉验证。两项同时指向不支持地区，几乎等于自证身份；只有一项对得上，同样会扣分——这正是"单项看起来没问题、整体却被封"的典型原因。

**失败判定**：东八区 + 不支持地区 IP → 2/10；仅时区为东八区 → 4/10；仅 IP 不支持 → 3/10；一致 → 10/10。

---

### 21. Claude 服务连通 【启发式】

**查什么**：分别探测三个域名是否可达。

| 域名 | 用途 |
|---|---|
| `api.anthropic.com` | 对话与账号接口 |
| `claude.ai` | 网页版入口 |
| `claudeusercontent.com` | 附件与产物内容分发 |

**隐藏规则**：只测一个域名会出现误判。分流规则漏了 `claude.ai` 时，App 内接口照常、网页版打不开；漏了 `claudeusercontent.com` 则表现为"能登录但传不了文件"。所以三个分开测。

**失败判定**：全部可达 → 10/10；缺 1 个 → 6/10；缺 2 个及以上 → 2/10。

**说明**：只验证连通性，不发送任何账号信息。

## 七、已知误判与边界

1. **中文字体**：几乎所有 Android 都预装 Noto CJK，"检出中文字体"区分度有限；真正有效的是厂商自有字体。
2. **支付环境是推断**：卡号、账单地址无法在本机读取，只能通过商店来源 + GMS + 支付应用组合推断；侧载安装会被判定为"非商店安装"。
3. **住宅代理无法 100% 识别**：如果代理服务商真的租用住宅宽带，IP 层面几乎无法与真实用户区分；PTR 异常是目前最有效的旁证，但仍可能漏判。
4. **机房 IP 名单是静态的**：新出现的小型 VPS 商不一定在名单内，此时依赖 hosting 标记与 PTR 兜底。
5. **口径差异**：proxycheck 的 `type=Business` 常把家宽也归为 Business（它按 ASN 分类），所以本项目把它当作"非机房非代理"而非"住宅"的正面证据，需要与 ip-api 的 `hosting=false` 叠加才给满分。
6. **不能检测的**：号码是否来自接码平台、号码是否已被他人用过、卡是否被盗刷过、账号历史关联——这些只有服务器侧有记录。

## 附：评分与结论

- 按权重分配总分 **100** 分，权重即该项的丢分上限。
- 单项得分 = 权重 × 得分率（得分率仍按 10 分制评估）。
- 得分率 <80% 且权重 ≥3 的项才计入"待改进"。
- 结论分档：≥85 可以放心使用 / 65–85 有一定风险 / <65 不建议使用。
- 命中否决项时，无论总分如何，结论一律为「请不要使用」。
